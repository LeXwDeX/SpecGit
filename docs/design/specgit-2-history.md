# SpecGit 2.0 historical requirement dispositions

Snapshot: 2026-09-09, 296 issues (290 closed, six open before new implementation
issues #509–#514). All 296 complete issue bodies were reviewed. The paginated
comment inventory contained 138 issue comments: 104 standard branch-association
markers were classified mechanically and 34 substantive comments were read.
PR comments are outside this issue-comment count; this is not a claim of reviewing
every historical PR diff or runtime. Historical closed state is preserved.

Use with the [architecture](specgit-2.md), [harness contract](specgit-2-contract.md)
and [feature acceptance matrix](specgit-2-acceptance.md). The destination issue
owns the listed 2.0 acceptance obligation, including proving removal for retired
mechanisms. A historical row retains a lesson, not an instruction to reopen old work.

- **retain**: preserve the externally observable requirement in Rust.
- **adapt**: preserve the WHY with native platform ownership or new harness behavior.
- **retire**: explicitly remove obsolete machinery and verify it is absent.
- **historical**: retain evidence/lesson without recreating a resolved old implementation.

Counts: adapt 147, historical 39, retain 100, retire 10.

Operative architecture/contract requirements take precedence if a condensed row
could be read as preserving the old custom closure, repair or reuse protocol.
The 1.x ready-time anchor is historical; current spec/head/attempt evidence stays
fresh without forcing unchanged product tests to rerun on a ready event.
Fixture cleanup and superseded releases never establish native completion.
